### Pre-build — AI requirement added late
**What happened:** Initial plan had no AI component; competition requires visible AI.
**What we tried first:** Considered calling an external LLM API for alert text.
**What we learned:** An API wrapper isn't defensible as "our AI" to a judge, and adds a dependency we can't rely on during a live demo.
**What we changed:** Added a real Isolation Forest ML model trained locally on satellite-derived features, with alert language generated by deterministic rules from the model's own score.

### Pre-build — Copernicus registration blocked development
**What happened:** Original satellite data plan used Copernicus Data Space Ecosystem, which requires account registration and authentication.
**What we tried first:** Attempted to register for API access.
**What we learned:** Registration friction was eating into the one-week timeline before any code was written.
**What we changed:** Switched satellite data provider to Element 84 Earth Search STAC API — no registration, no authentication, queryable directly.

### Pre-build — Full stack too heavy for one week
**What happened:** Original plan (GitHub Actions + Supabase + Vercel + full pipeline) was scoped for multiple weeks.
**What we tried first:** Considered dropping live satellite data entirely for a faster demo.
**What we learned:** Live data and real ML were both non-negotiable requirements from the team.
**What we changed:** Removed Supabase from the stack entirely — data now lives as versioned files in the repo — to cut one full service integration out of the timeline.

### 2026-09-07 — Earth Search STAC search API unreachable from the build environment
**What happened:** The STEP 0 connectivity check against `https://earth-search.aws.element84.com/v1/search` failed. Every request died at the network egress proxy with `Tunnel connection failed: 403 Forbidden` — the host is not on this environment's allowlist. The proxy status endpoint confirmed a `connect_rejected` policy denial for `earth-search.aws.element84.com:443`.
**What we tried first:** Retried the POST directly with `requests`, then checked whether it was a TLS/CA problem rather than a policy problem, by reading `/root/.ccr/README.md` and querying `$HTTPS_PROXY/__agentproxy/status`.
**What we learned:** It is a hard organisational egress denial, not a bug and not something to retry around. Critically though, we probed the neighbouring hosts and found that `sentinel-cogs.s3.us-west-2.amazonaws.com` — the S3 bucket the STAC API actually indexes — **is** reachable. Earth Search is only a search index over that bucket. The bucket stores, inside every scene directory, the exact same STAC item JSON the API would have returned, and it permits anonymous `ListObjectsV2`.
**What we changed:** Wrote `pipeline/search.py`, which replaces the STAC search API with direct S3 prefix listing (`sentinel-s2-l2a-cogs/{zone}/{band}/{square}/{year}/{month}/`) plus a per-scene item-JSON fetch. Same data, same STAC schema, still no account and no API key. Note for the notebook: this is arguably *more* robust than the original plan — it removes a third-party search service from the critical path and leaves only AWS S3.

### 2026-09-07 — Tile-level cloud filter returns almost no usable scenes over Ghana
**What happened:** With the specified filter `eo:cloud_cover < 20`, an 18-month search returned **3 scenes** for tile T30NXM and **9** for T30NXL. An Isolation Forest cannot be trained on 3 readings.
**What we tried first:** Assumed the search was broken and widened the date range; then dumped the full cloud-cover distribution for both tiles across 18 months.
**What we learned:** The search was fine — southern Ghana is genuinely that cloudy. Median tile cloud cover is **84.9%** (T30NXM) and **69.0%** (T30NXL). But `eo:cloud_cover` is a statistic for the whole **110 km × 110 km tile**, while each monitoring point is a ~100 m window. A tile can be 80% cloudy overall and still be perfectly clear over our specific river pixel, so a tile-level threshold throws away most of the usable data for no reason.
**What we changed:** Dropped the tile-level threshold to a loose sanity filter and moved cloud rejection to the **pixel** level, using the per-scene SCL band inside the point window (reject SCL classes 3, 8, 9, 10 — shadow, cloud medium, cloud high, cirrus). This is the filter that actually matters and it recovers roughly an order of magnitude more readings.

### 2026-09-07 — SCL water class does not detect the Pra River
**What happened:** STEP 1 specified selecting water pixels via SCL class 6. On the clearest available scene (0.47% cloud, 2026-01-25), a 10 km × 10 km box around the control point contained exactly **1** SCL-water pixel out of 250,000. The monitor point's box had 33; the intake's had 407.
**What we tried first:** Ran the NDTI reader on six scenes at the control point — every one returned "0 usable water pixels", including a completely cloud-free scene whose window classified as 100% vegetation.
**What we learned:** Two separate problems. (a) The Pra is a narrow river — at 20 m SCL resolution it is only 2–5 pixels wide, so it barely registers. (b) More fundamentally, SCL's water classifier keys on the low reflectance of clear water, and the Pra is *heavily sediment-laden* — the exact condition this project exists to measure. Turbid water is spectrally close to bare soil, so SCL systematically misclassifies precisely the pixels we care about most. Using SCL to find water would bias the dataset against polluted water: a self-defeating filter.
**What we changed:** Switched water detection to **MNDWI** = (green − SWIR16) / (green + SWIR16). Short-wave infrared is strongly absorbed by water regardless of how much sediment it carries, so MNDWI stays reliable on turbid rivers. On the same clear scene MNDWI recovered a coherent river channel where SCL found nothing. SCL is still used, but only for its reliable job — rejecting cloud and shadow pixels.

### 2026-09-07 — All three supplied monitoring coordinates are off the river
**What happened:** The three coordinates in the project brief do not sit on water. Measured against the clearest scene, distance from the coordinate to the nearest detected water pixel: **control 1,785 m**, **monitor 288 m**, **intake 540 m**.
**What we tried first:** Assumed the NDTI reader was misaligned and re-verified the coordinate transform (WGS84 → EPSG:32630) and the MGRS tile derivation independently. Both were correct — the control point resolves to T30NXM at E649359/N686609, and the window genuinely contains vegetation and bare soil, not river.
**What we learned:** The brief already flagged this risk ("verify these actually sit on water ... replace if wrong") and the flag was justified. The control point is the worst of the three: 1.8 km from any water, so it would have produced pure land readings and silently destroyed the control-suppression logic that the entire alert design depends on — a rainfall spike would never have been suppressed, because the "control river" was never a river.
**What we changed:** Blocked further pipeline work on this and escalated to the team for a coordinate decision, rather than silently snapping each point to whatever water happened to be nearest — the nearest water to a point is not necessarily the Pra, and for the intake point in particular it matters that we measure the river *at the abstraction point*, not an adjacent pond or flooded pit.

### 2026-09-07 — Band offset produced infinite index values
**What happened:** The first MNDWI pass returned values ranging from `-inf` to `30,494,268` instead of the expected −1…1.
**What we tried first:** Assumed corrupt pixels or a nodata value leaking through the mask.
**What we learned:** Sentinel-2 processing baseline ≥ 04.00 applies a BOA reflectance offset — these scenes carry `scale: 0.0001, offset: -0.1`. After the offset, low-reflectance bands legitimately go slightly negative, so a normalized-difference denominator (green + SWIR) can pass through ~0 and blow up. The scale factor cancels in a normalized difference, but the **offset does not** — it must be applied, and then guarded against.
**What we changed:** Read `scale`/`offset` per scene from the STAC item's `raster:bands` (never hardcoded — older baselines use offset 0), and require a denominator above a small epsilon before dividing. Index values are now bounded in the physical range.
