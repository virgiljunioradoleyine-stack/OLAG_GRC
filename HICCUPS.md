### Pre-build — AI requirement added late
**What happened:** Initial plan had no AI component; competition requires visible AI.
**What we tried first:** Considered calling an external LLM API for alert text.
**What we learned:** An API wrapper isn't defensible as "our AI" to a judge, and adds a dependency we can't rely on during a live demo.
**What we changed:** Added a real Isolation Forest ML model trained locally on satellite-derived features, with alert language generated by deterministic rules from the model's own score.

### Pre-build — Copernicus registration blocked development
**What happened:** Original satellite data plan used Copernicus Data Space Ecosystem, which requires account registration and authentication.
**What we tried first:** Attempted to register for API access.
**What we learned:** Registration friction was eating into the one-week timeline before any code was written.
**What we changed:** Switched satellite data provider to Element 84 Earth Search STAC API — no registration, no authentication, queryable directly.

### Pre-build — Full stack too heavy for one week
**What happened:** Original plan (GitHub Actions + Supabase + Vercel + full pipeline) was scoped for multiple weeks.
**What we tried first:** Considered dropping live satellite data entirely for a faster demo.
**What we learned:** Live data and real ML were both non-negotiable requirements from the team.
**What we changed:** Removed Supabase from the stack entirely — data now lives as versioned files in the repo — to cut one full service integration out of the timeline.

### 2026-09-07 — Earth Search STAC search API unreachable from the build environment
**What happened:** The STEP 0 connectivity check against `https://earth-search.aws.element84.com/v1/search` failed. Every request died at the network egress proxy with `Tunnel connection failed: 403 Forbidden` — the host is not on this environment's allowlist. The proxy status endpoint confirmed a `connect_rejected` policy denial for `earth-search.aws.element84.com:443`.
**What we tried first:** Retried the POST directly with `requests`, then checked whether it was a TLS/CA problem rather than a policy problem, by reading `/root/.ccr/README.md` and querying `$HTTPS_PROXY/__agentproxy/status`.
**What we learned:** It is a hard organisational egress denial, not a bug and not something to retry around. Critically though, we probed the neighbouring hosts and found that `sentinel-cogs.s3.us-west-2.amazonaws.com` — the S3 bucket the STAC API actually indexes — **is** reachable. Earth Search is only a search index over that bucket. The bucket stores, inside every scene directory, the exact same STAC item JSON the API would have returned, and it permits anonymous `ListObjectsV2`.
**What we changed:** Wrote `pipeline/search.py`, which replaces the STAC search API with direct S3 prefix listing (`sentinel-s2-l2a-cogs/{zone}/{band}/{square}/{year}/{month}/`) plus a per-scene item-JSON fetch. Same data, same STAC schema, still no account and no API key. Note for the notebook: this is arguably *more* robust than the original plan — it removes a third-party search service from the critical path and leaves only AWS S3.

### 2026-09-07 — Tile-level cloud filter returns almost no usable scenes over Ghana
**What happened:** With the specified filter `eo:cloud_cover < 20`, an 18-month search returned **3 scenes** for tile T30NXM and **9** for T30NXL. An Isolation Forest cannot be trained on 3 readings.
**What we tried first:** Assumed the search was broken and widened the date range; then dumped the full cloud-cover distribution for both tiles across 18 months.
**What we learned:** The search was fine — southern Ghana is genuinely that cloudy. Median tile cloud cover is **84.9%** (T30NXM) and **69.0%** (T30NXL). But `eo:cloud_cover` is a statistic for the whole **110 km × 110 km tile**, while each monitoring point is a ~100 m window. A tile can be 80% cloudy overall and still be perfectly clear over our specific river pixel, so a tile-level threshold throws away most of the usable data for no reason.
**What we changed:** Dropped the tile-level threshold to a loose sanity filter and moved cloud rejection to the **pixel** level, using the per-scene SCL band inside the point window (reject SCL classes 3, 8, 9, 10 — shadow, cloud medium, cloud high, cirrus). This is the filter that actually matters and it recovers roughly an order of magnitude more readings.

### 2026-09-07 — SCL water class does not detect the Pra River
**What happened:** STEP 1 specified selecting water pixels via SCL class 6. On the clearest available scene (0.47% cloud, 2026-01-25), a 10 km × 10 km box around the control point contained exactly **1** SCL-water pixel out of 250,000. The monitor point's box had 33; the intake's had 407.
**What we tried first:** Ran the NDTI reader on six scenes at the control point — every one returned "0 usable water pixels", including a completely cloud-free scene whose window classified as 100% vegetation.
**What we learned:** Two separate problems. (a) The Pra is a narrow river — at 20 m SCL resolution it is only 2–5 pixels wide, so it barely registers. (b) More fundamentally, SCL's water classifier keys on the low reflectance of clear water, and the Pra is *heavily sediment-laden* — the exact condition this project exists to measure. Turbid water is spectrally close to bare soil, so SCL systematically misclassifies precisely the pixels we care about most. Using SCL to find water would bias the dataset against polluted water: a self-defeating filter.
**What we changed:** Switched water detection to **MNDWI** = (green − SWIR16) / (green + SWIR16). Short-wave infrared is strongly absorbed by water regardless of how much sediment it carries, so MNDWI stays reliable on turbid rivers. On the same clear scene MNDWI recovered a coherent river channel where SCL found nothing. SCL is still used, but only for its reliable job — rejecting cloud and shadow pixels.

### 2026-09-07 — All three supplied monitoring coordinates are off the river
**What happened:** The three coordinates in the project brief do not sit on water. Measured against the clearest scene, distance from the coordinate to the nearest detected water pixel: **control 1,785 m**, **monitor 288 m**, **intake 540 m**.
**What we tried first:** Assumed the NDTI reader was misaligned and re-verified the coordinate transform (WGS84 → EPSG:32630) and the MGRS tile derivation independently. Both were correct — the control point resolves to T30NXM at E649359/N686609, and the window genuinely contains vegetation and bare soil, not river.
**What we learned:** The brief already flagged this risk ("verify these actually sit on water ... replace if wrong") and the flag was justified. The control point is the worst of the three: 1.8 km from any water, so it would have produced pure land readings and silently destroyed the control-suppression logic that the entire alert design depends on — a rainfall spike would never have been suppressed, because the "control river" was never a river.
**What we changed:** Blocked further pipeline work on this and escalated to the team for a coordinate decision, rather than silently snapping each point to whatever water happened to be nearest — the nearest water to a point is not necessarily the Pra, and for the intake point in particular it matters that we measure the river *at the abstraction point*, not an adjacent pond or flooded pit.

### 2026-09-07 — BOA offset applied twice, silently inverting the water index
**What happened:** Our first index pass returned values from `-inf` to `30,494,268` instead of −1…1. We "fixed" it with a denominator guard and moved on. That was treating the symptom. The real bug surfaced later, when a positive control failed: **Lake Bosumtwi** — an 8 km-wide crater lake, the most unambiguous water in Ghana — came back from our water detector as *"NO PERSISTENT WATER within 1 km"*.
**What we tried first:** Initially we read `offset: -0.1` from each scene's `raster:bands` metadata and applied it, believing this was the Sentinel-2 processing-baseline ≥ 04.00 BOA offset that must be applied to get real reflectance. The infinite values seemed to be an unrelated divide-by-zero, so we added a `denominator > 0.02` guard and considered it handled.
**What we learned:** Dumping raw pixels over Bosumtwi made it obvious: green = −0.039 and SWIR = −0.082. Reflectance is physically impossible below zero, so our conversion was wrong, not the data. Earth Search's COGs have **already had the BOA offset applied** — the scene property `earthsearch:boa_offset_applied: true` says so — while `raster:bands` still advertises the offset that *would* be needed for unharmonised data. We were subtracting 0.1 a second time. That shifts every band down, drives dark surfaces (water most of all) negative, and then a normalized difference divides by a negative denominator and **flips sign**. Water was being scored as not-water. The infinities were the same bug, and our denominator guard was quietly discarding the clearest water instead of fixing it.
**What we changed:** `_band_scaling()` now checks `earthsearch:boa_offset_applied` and skips the offset when it is already in the pixels — read per scene, never hardcoded, since older baselines genuinely do need it. Bosumtwi now reads 10,000 of 10,000 pixels as water. **The lesson we're keeping:** the first three points we tested were all off-river, so *every* result was "no water" and everything looked consistent. A bug that agrees with your expectations is invisible. It only surfaced because we tested somewhere the answer was already known. We now keep Bosumtwi as a standing positive control.

### 2026-09-07 — Vercel rejected the first deploy over a Next.js CVE

**What we tried first:** We had scaffolded with Next.js 15.5.4, which was simply what we reached for.

### 2026-09-07 — Deployed dashboard was not publicly reachable
**What happened:** After the Next.js CVE fix the deploy went green, but fetching the production URL returned `302 Found` redirecting to `vercel.com/sso-api`.
**What we tried first:** Assumed the build had not finished propagating and re-fetched.
**What we learned:** It was not a propagation delay. The Vercel team applies **Deployment Protection (Vercel Authentication)** to new projects by default, so every visitor must log in to the Vercel account first. A "successful deploy" is therefore not the same as a reachable page — and a judge following our link during evaluation would have hit a login wall, with us none the wiser because it works fine for whoever is signed in.
**What we changed:** Flagged for the team to disable under Project Settings → Deployment Protection, and added "open the dashboard URL in a private browser window" to the demo checklist. Testing a public link while logged in proves nothing.

### 2026-09-07 — Band misalignment at tile edges gave confidently wrong coordinate checks
**What happened:** Our coordinate verifier reported the `monitor` point as sitting on 21 water pixels. The data collector, reading the same point from the same scenes, found no channel at all. Both could not be right.
**What we tried first:** Assumed the collector's smaller reading window was at fault and enlarged it. That changed the answer — nearest water moved between 0 m and 122 m depending only on how big a box we asked for, which is impossible for a fixed point on a fixed river.
**What we learned:** Sentinel-2 bands come at different resolutions (10 m red/green, 20 m SWIR/SCL), so they have to be resampled onto a shared grid. We were reading one band and then reading the others with `out_shape` set to *that band's* shape. In the middle of a tile this is harmless. At a tile edge it is not: rasterio clips a window that runs past the raster, each band loses a different number of its own pixels, and forcing the clipped arrays to a common shape stretches misaligned data over each other. No exception, no warning — the arrays simply stop describing the same ground. The `monitor` point sits ~330 m from the northern edge of T30NXL, which is why it was affected and the other two were not.
**What we changed:** Added `pipeline/raster.py`, which defines the target grid explicitly from the requested bounds and reads every band onto it with a boundless read, so out-of-raster area comes back as nodata instead of shifting the grid. Results are now identical at every window size. **The correction that matters:** re-verified with the fix, the team's original coordinate (5.423526, −1.628935) was on the channel all along at 14 px. Our "off channel" verdict on it was the bug, and the "better" coordinate we suggested in its place was genuinely off-channel by 153 m. We had told the team their coordinate was wrong and handed them a worse one. Every coordinate verdict issued before this fix was re-run.

### 2026-09-07 — Eighteen months of history is not enough to train on
**What happened:** The first full collection over the 18 months specified in the brief produced **20 readings** for the control point and **27** for the intake, from ~160 scenes each. An Isolation Forest needs considerably more than that to learn a seasonal baseline.
**What we tried first:** Checked whether the yield was a bug. It is not: 12–17% of scenes are usable, which is simply what the Pra basin's cloud cover allows once per-pixel filtering has done its job.
**What we learned:** The constraint is not our filtering, it is the sky. But the 18-month window was an assumption in the brief, not a limit of the data — the Sentinel-2 L2A archive on AWS reaches back to **2017**, and we confirmed all twelve months are present for every year since. Nine years at the same yield gives roughly 120–160 readings per point instead of 20.
**What we changed:** Extended collection to the full archive from 2017-01-01. Beyond simply having more data, this gives the model several complete wet/dry cycles, so seasonal turbidity is learned as normal rather than flagged as an anomaly every rainy season — which a single 18-month window could never have taught it.

### 2026-09-07 — The model missed the one documented pollution event
**What happened:** We found a precisely dated, independently reported incident to test against: on 14 August 2026 raw-water turbidity at the Daboase intake hit **11,955 NTU** against a 500 NTU limit — about 24× over. Our two nearest readings (18 and 20 August) were scored **NORMAL**, at the 95th percentile of ordinariness. The system would have warned nobody.
**What we tried first:** Assumed the readings had simply not been collected, or that cloud had removed the relevant scenes. Neither: both dates produced clean readings over the full 88-pixel channel mask.
**What we learned:** Three independent causes, and the first is the serious one. **(a) NDTI is insensitive at high sediment loads.** It is a normalised index, so when turbidity rises far enough both red and green brighten together and the ratio barely moves. Reading the raw bands showed red reflectance at **0.37–0.39** on the event dates versus 0.19–0.22 on the dates NDTI ranked as most turbid — nearly double the brightness, while NDTI ran the *opposite* way (0.12 vs 0.23). Our chosen index ranks the worst recorded event as calmer than a routine January. **(b) The control point is blind in the rainy season** — zero July–September readings in 2023, 2024, 2025 and 2026, and nothing at all since 19 June 2026. For the August event no control reading fell within the matching window, so the suppression feature was inert on the one date it mattered. Galamsey turbidity peaks when cloud peaks. **(c) Latency**: nearest observations were 4 and 6 days late, which is a structural ceiling of a 5-day revisit, not a model problem.
**What we changed:** Recorded the failure in full in `TEST_RESULTS.md` rather than reporting only the tests that passed — the control-suppression and false-positive results look good, and would be misleading quoted on their own, because a low false-positive rate is trivially achievable by being insensitive, which we now know we are. `fetch.py` now stores raw `red` and `green` per reading so the next collection can feed absolute reflectance to the model alongside NDTI. We are *not* dropping NDTI: absolute reflectance also rises with atmospheric haze, which is why a normalised index was chosen originally. The fix is to give the model both and let the control point reject the common-mode atmospheric part — which puts more weight on fixing the control point's rainy-season blindness.

### 2026-09-07 — Isolation Forest flagged clean water as anomalous
**What happened:** Reviewing flagged dates, more than half were turbidity *falling* sharply, not rising — the river becoming unusually clean. At contamination 0.05 the monitor point had 13 flags, 10 with a flat control, but only **4** were actually rises.
**What we tried first:** Read the flags as candidate pollution events and started matching them against dates, which is when the negative deltas became obvious (2025-01-25 at Δ −0.2894, 2023-11-27 at Δ −0.1881).
**What we learned:** Obvious in hindsight and easy to miss: an Isolation Forest detects *outliers*, not *bad* outliers. It has no notion that dirty water matters and clean water does not. Left alone it would have more than doubled our alert count, most of them announcing good news to a water treatment plant.
**What we changed:** Added a direction check to the alert rules: a flagged reading whose turbidity has fallen is reported as NORMAL with a note, never escalated. This is the step that turns "statistically unusual" into "worth warning someone about", and it is a good example for the notebook of why an ML output needs domain rules wrapped around it rather than being surfaced raw.

### 2026-09-07 — The scheduled run would have rebuilt the channel mask from cloudy scenes
**What happened:** Reviewing the monitoring job before trusting it on a cron, we found `collect()` rebuilding the channel mask from whatever scenes the run happened to fetch. A scheduled run looks back only ~30 days, so the mask would be derived from ~6 recent scenes instead of the clearest 12 in a nine-year archive.
**What we tried first:** Nothing — this was caught by reading the job's behaviour rather than by it failing. The CI run passed, because it happened to execute in a period with usable scenes.
**What we learned:** Two problems, and the failure mode is quiet in both. The mask defines *which pixels every reading is measured over*, so a mask that changes between runs makes readings from different runs incomparable — an apparent turbidity change could just be a change in which pixels were sampled. Worse, in the rainy season a 30-day window can contain no scene clear enough to derive a mask from at all, and the code path for that is `"no channel mask, skipping"` — the job would silently collect nothing during exactly the season pollution events happen in. Same shape as the control-point blindness in TEST_RESULTS.md §1(b): the system degrades quietly when the weather is worst.
**What we changed:** The mask is now built once from the clearest scenes across the whole archive, saved to `data/masks/{point}.npy`, committed, and reused by every subsequent run. Rebuilding is explicit (`rebuild=True`) rather than incidental.

### 2026-09-07 — Schema change wrote the literal text "nan" into 460 historical rows
**What happened:** After adding `red` and `green` columns to the readings CSVs (so the next collection can feed absolute reflectance to the model), the next monitoring run rewrote every historical row with `nan` in those two columns — 460 rows across two files.
**What we tried first:** Considered reverting the schema change and only adding the columns during a future full re-collection.
**What we learned:** The rewrite itself was correct — the merge preserves old rows and old rows genuinely have no value for a column that did not exist when they were collected. The bug was how the absence was written. Python's `csv` writer stringifies a float NaN as the text `nan`, which *looks like data*. Anyone reading the file, or a tool with slightly different null handling, could take it for a value. An empty cell says "missing" unambiguously to pandas and to a person.
**What we changed:** `write_csv` now blanks missing values instead of stringifying them, and we kept the new columns rather than deferring them — settling the file format once is better than flipping it again after the re-collection. Verified all three files still parse with zero nulls in the columns that matter.

### 2026-09-07 — The control point is correctly sited, and still cannot be shown to work
**What happened:** With the control confirmed on the Pra mainstem and above the Pra/Offin confluence — the arrangement the whole alert design depends on — we tested whether it actually behaves like a control. It does not, measurably.
**What we tried first:** Assumed the risk was contamination: that galamsey upstream of the control would dirty it at the same time as the monitored points, so the system would see "everything rose" and suppress real alerts. We checked the imagery, found extensive stripped riverbed immediately upstream, and tried to prove it was expanding by measuring bare ground each dry season from 2017. That measurement failed to support the claim — 88 ha in 2017 against 114 ha in 2026, but 39 ha in 2025, with year-to-year scatter as large as the trend because dry-season timing shifts vegetation and exposed riverbed by weeks. We could not honestly say the mining is growing.
**What we learned:** The real problem was elsewhere, and the sanity check found it. The control's date-to-date NDTI changes correlate with the monitored points at r = 0.20–0.25, agreeing in direction on ~52% of dates — a coin flip. But `monitor` and `intake`, two points on the *same river*, 22 km apart, read from the *same tile* on the *same dates*, agree barely better (r = 0.28, 57%). That comparison is what makes it interpretable: if the best case we can construct is nearly as bad as the control, the problem is not where the control sits. It is that a reading is mostly noise. Comparing readings taken ≤3 days apart (when the river genuinely cannot have changed much) against readings ≥20 days apart implies roughly **80% of the monitor point's apparent variation is measurement noise**. Within-scene pixel scatter alone is 0.020–0.030 NDTI against a total date-to-date spread of 0.052–0.061.
**What we changed:** Corrected what we claim. TEST_RESULTS.md §2 previously presented five "correctly suppressed" spikes as evidence the control logic works; it now says plainly that with ~52% direction agreement roughly half of any spike set will show the control rising by chance, so those five may be coincidence. The notebook should claim the control is *designed* to suppress false alarms, not that it has been shown to. The fixes point the same way as the missed-event finding: sample a length of channel instead of a 100 m box to get more pixels per reading, use absolute reflectance alongside the normalised index, and smooth over time before comparing points. **The lesson worth writing up:** we nearly reported a passing test. The suppression cases looked like the logic working, and only a deliberate sanity check — comparing two points that *should* agree — revealed that nothing in this data agrees with anything.

## Phase 2 — building the full platform

### 2026-09-07 — The development sandbox blocks every data source we needed
**What happened:** Rebuilding the project around real environmental data meant reaching CHIRPS, NASA POWER, Overpass, HydroSHEDS and map-tile servers. Every one returned `000` — the sandbox's egress policy allows only the Sentinel-2 bucket, PyPI, npm and GitHub.
**What we tried first:** Probing each host directly, which established the block but not whether the sources themselves were usable.
**What we learned:** The constraint is local, not universal. GitHub Actions runners have unrestricted internet, and we had already proved that when the monitoring workflow reached the Sentinel-2 bucket from CI. So CI can serve as the verification harness for network code that cannot be tested locally.
**What we changed:** Wrote `scripts/probe_sources.py` and a `probe.yml` workflow that tests every candidate source from CI and reports status, content type and a payload sample. The results (`data/sources/probe_evidence.json`) turned architecture guesses into evidence: NASA POWER and Open-Meteo both work as anonymous JSON point APIs; Overpass works; **HydroRIVERS returns 403 behind a Cloudflare interstitial** and cannot be fetched programmatically at all; `data.gov.gh` refuses connections outright. Every source decision in the build now cites that file.

### 2026-09-07 — Our own leakage test caught our own leakage
**What happened:** The new feature builder was written to be strictly causal, and a test was written alongside it that mutates *all* data after a cut date and asserts no earlier feature changes. On first run it failed: `rain_7d_anom` and `rain_30d_anom` moved.
**What we tried first:** Nothing — the test caught it before the code was ever committed.
**What we learned:** The rainfall anomaly compares a window against a day-of-year climatology, and we had built that climatology from "other years", which is the intuitive phrasing and is wrong. Other years includes *later* years. A 2019 observation's anomaly was partly determined by 2023 rainfall — information that would not exist at prediction time. It is exactly the same class of mistake the audit found in the old control-matching code, arrived at independently, which is a useful lesson about how easily this happens.
**What we changed:** Climatology is prior-years-only, matching the seasonal baseline. The cost is no anomaly value for the first couple of seasons, which is the correct price. **The wider point for the notebook:** we did not find this by being careful, we found it because a test made the property checkable. Causality is not something you can eyeball in a feature builder.

### 2026-09-07 — Cloud fraction was the wrong quality gate
**What happened:** With quality thresholds set by judgement before any data existed, 1,236 of 2,456 real observations came back LOW_QUALITY — the majority of the record.
**What we tried first:** Assumed the thresholds were merely a bit tight and considered loosening them, which would have been moving the goalposts to get a nicer number.
**What we learned:** Checking which criterion was binding showed 70% of observations failed on cloud fraction alone (>20% of the reach masked), against 32% on pixel count and 9% on spatial scatter. But cloud fraction is the wrong thing to gate on: if 80% of a reach is under cloud and the clear fifth still yields 300 water pixels, that is a perfectly good measurement of the river. Pixel count already captures whether enough water was seen. Cloud fraction matters only for whether the visible part is *representative* of the reach — a secondary concern.
**What we changed:** Pixel count leads, cloud fraction is secondary and weighted accordingly (GOOD ≤50%, ACCEPTABLE ≤85%). GOOD rose from 698 to 1,028 observations. The thresholds are now calibrated against the real distribution and the reasoning is recorded in the code rather than being a bare constant.

### 2026-09-07 — Negative reflectance pushed MNDWI to 2.3
**What happened:** New schema tests, running against real data for the first time, failed: 25 observations had MNDWI outside [-1, 1], reaching 2.30, and three had negative SWIR reflectance.
**What we tried first:** Checked whether the affected rows were simply bad observations that should be filtered. They were not — several were GOOD quality with 600+ water pixels.
**What we learned:** Sentinel-2 L2A atmospheric correction can return slightly negative reflectance over very dark targets such as clear water. It is a known processing artifact, not corrupt data. But a normalised difference divides by the sum of two bands, and a small negative SWIR shrinks that denominator, so the ratio escapes its mathematical range. This is the third distinct bug in this project caused by normalised-difference denominators; they are a recurring hazard.
**What we changed:** Reflectance is floored at zero before any index is computed — negative reflectance is unphysical, so clipping it is a correction rather than a fudge — and the denominator must exceed a meaningful epsilon. Every index is now provably inside [-1, 1], and the schema test that caught this runs in CI on every push.

### 2026-09-07 — Storing observations nothing was allowed to use
**What happened:** 137 observations were written with quality REJECTED, meaning too few water pixels to be a measurement at all.
**What we learned:** A rejected row is not a measurement of the river, but it sits in the dataset looking like one: it has a date, a station, an index value. Anything reading the CSV without also checking the quality column would use it. The safest place to enforce that is at the point of creation, not at every point of consumption.
**What we changed:** Rejected observations are dropped at source and never written. A test asserts the dataset contains none.

### 2026-09-07 — The first production pipeline run failed, and that was the system working
**What happened:** The first full run of `pipeline.yml` in CI collected 2,993 observations successfully and then **failed at the dataset-validation step**, skipping export and commit.
**What we tried first:** Nothing — the failure was the point. The workflow is built so that validation runs *before* anything downstream consumes the data, and the export and commit steps are conditional on it passing. It refused to publish, which is exactly the behaviour asked for.
**What we learned:** Two genuine defects, both ours. First, trivially, `pipeline.yml` installed `requirements.txt` while the validation step runs pytest, which lives in `requirements-dev.txt` — so validation could never have run at all. Second, and more serious, the run's own log exposed nonsense river distances: **323 km of river between P02 and P03 for a 32 km straight line**, and 267 km between P05 and P06 for 13 km. Overpass returns a river as many *disjoint* ways in arbitrary order, and our cumulative walk over their concatenated vertices was jumping between pieces that are not connected to each other. The local test could not have caught this because Overpass is unreachable from the dev sandbox — only a real response revealed it.
**What we changed:** Installed dev requirements in the pipeline. Added a per-segment plausibility check: real channel sinuosity (river length ÷ straight-line length) sits roughly between 1 and 3, so anything outside that is rejected, replaced with a straight-line estimate scaled by a typical sinuosity, and explicitly labelled `method="straight_line_estimate"` so the dashboard never presents an estimate as a measurement. Five tests now cover it, including one that feeds the builder deliberately disjoint geometry. **Worth recording for the notebook:** we had verified this code path locally against a *fallback*, never against a real Overpass response, and it passed. The bug lived precisely in the gap between what we could test and what production actually does — which is the argument for making the pipeline fail loudly rather than publish quietly.

### 2026-09-07 — Thin cloud was getting into readings the quality gate called GOOD
**What happened:** After the merge-precedence fix healed the out-of-range MNDWI rows, one schema test still failed, and chasing it exposed something worse than the assertion. Thirty-one observations carried a green reflectance above 1.0, peaking at 1.667, with red, green and NIR all sitting flat around 1.1 and SWIR much lower. That flat bright visible spectrum is cloud, not water. Eighteen were LOW_QUALITY, ten ACCEPTABLE — and three were labelled **GOOD**, which means the quality gate was certifying cloud tops as valid river measurements.
**What we tried first:** Treating it as a bad test bound. The first instinct was that Sentinel-2 BOA reflectance can legitimately exceed 1.0 over bright targets, so the fix was to raise the ceiling from 1.6 to something that accommodated the data. That would have passed CI and preserved the contamination.
**What we learned:** Two things. The scene classification layer we rely on for cloud rejection has a known blind spot for thin cirrus over water, and MNDWI does not catch it either — SWIR stays low under haze, so the contaminated pixels still score as water and pass the mask. Nothing in the chain was checking the one property that actually separates the two: **water is dark**. Even a river carrying heavy sediment stays below about 0.35 in green; the median across our whole archive is 0.20. The distribution is cleanly bimodal — it runs smoothly up to roughly 0.5 and then jumps to 1.0 and above, with nothing in between. There was a gap to cut in, and no judgement call to make about where.
**What we changed:** A per-pixel brightness rejection in the collector: any pixel above 0.5 reflectance in red or green is excluded from the reading, and counted into the reported contamination fraction so the quality score sees the obstruction the classifier missed. Per *pixel*, deliberately — a single cloud edge should shrink a reading, not discard the window. The schema test now asserts the invariant the collector guarantees rather than a bound picked to fit the data, so if the rejection ever stops working the test says so. **The lesson worth writing up:** the failing test was right and our first reading of it was wrong. Loosening a bound until data fits is indistinguishable, from the outside, from fixing a bug — and here it would have shipped cloud reflectance into the anomaly model as if it were river sediment. The question to ask a failing assertion is not "is this bound too strict" but "what would have to be true of the data for this bound to be correct."

### 2026-09-07 — The brightness cut worked, and the bad rows survived anyway
**What happened:** The full re-collection ran, collected 2,931 fresh observations, wrote 2,319 — and the validation still failed with `red reaches 1.5376`, byte-for-byte the same maximum as before. The fix had done nothing visible.
**What we tried first:** Suspected the brightness cut was not being applied — a workflow input not taking, or the filter sitting in the wrong place. It was applied. The reading path cannot produce a red median above 0.5 any more; that is arithmetically impossible once every pixel above 0.5 is dropped.
**What we learned:** The contaminated rows were not being *recomputed*, they were being *preserved*. Merge precedence says a freshly collected row supersedes the stored one for the same station-date. But the brightness cut rejected every pixel in those 31 readings, so those dates produced no fresh row at all — and a row that does not exist cannot supersede anything. `best.update(fresh)` only replaces keys present in `fresh`. This is the second time the same hole has opened in the same function: the first version preferred whichever row had more pixels, which meant stale rows could never be healed; superseding by station-date fixed healing but still could not express *deletion*.
**What we changed:** A re-collection is now authoritative over the window it covered. For any station that produced data in the run, stored rows from the start date onward are replaced wholesale by what the run found; history before that date is untouched. The guard is per station — a station that returned nothing at all keeps its stored rows, so a transient read failure cannot erase nine years of record. Three tests cover the three cases: a rejected date disappears, a 90-day window does not reach into history, and an unread station is treated as unread rather than empty. **The lesson worth writing up:** we had been thinking of a re-collection as a set of updates, and it is really a statement about a time window. Under the update model there is no way to say "this reading should not exist", which is exactly what a fix to the *acceptance* criteria needs to say. A pipeline that can only add and amend will quietly carry its old mistakes forward forever.

### 2026-09-07 — The test suite was overwriting published data
**What happened:** After the successful pipeline run, `git status` showed `data/hydrology/network.json` modified locally, with the published river distances replaced by straight-line fallbacks.
**What we tried first:** Assumed it was harmless local noise from the sandbox being unable to reach Overpass, and nearly checked it out and moved on.
**What we learned:** Nothing had *run* the fetcher — the test suite had. `build_network` wrote to the production `data/hydrology/network.json` unconditionally, and four tests call it, one of which feeds it **deliberately disjoint fake geometry** to prove the sinuosity check fires. Whichever test ran last left its output in the real published file. It had not corrupted anything committed yet only because the workflow that commits data runs a narrower test selection — a coincidence of configuration, not a safeguard.
**What we changed:** `build_network` takes a `path`, and `path=None` computes without persisting; the tests pass it. A regression test reads the published file before and after building and asserts it is untouched, and separately proves writing still works when asked.
**What it exposed on the way:** Checking the file's real contents to see what had been lost showed the published version was itself wrong — station chainage read 277 km at P01, 10 km at P02, 334 km at P03. Chainage was being read straight off the cumulative centreline walk, which is the exact quantity the sinuosity check exists to distrust, so the *segment* distances were repaired while the *station* distances kept the raw disjoint-way artifact. It is now accumulated from the validated segments, so it is monotonic downstream and consistent with the distances published beside it. **The lesson worth writing up:** we fixed the symptom we were shown and not the source. The bad walk fed two outputs, one was checked, and nobody asked what else drank from it.
